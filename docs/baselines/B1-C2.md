# B1-C2: Hybrid PQC VDAM Baseline

## Purpose and boundary

B1-C2 is the four-party wallet-mediated VDAM baseline with hybrid post-quantum cryptography. Its intended business lifecycle and authorization semantics parallel B1-C0. The primary change is the cryptographic construction used for application signatures, DAS confidentiality, Keycloak integration, sender binding, and protected transport paths.

Repository root: `wallet-vc-model/`

The root `docker-compose.yml` includes all three clusters. Cluster-specific Compose files support multi-VM deployment.

## Business lifecycle

B1-C2 uses the same two benchmark modes as B1-C0:

- Initial mode performs Wallet authentication, OAuth authorization, OID4VCI proof, Authorization Credential issuance, and local storage.
- Repeated mode obtains a DAS challenge, requests user delegation, creates a Delegation VC plus KB-JWT and encrypted DAS package, builds a TPP presentation, exchanges it at `/token`, and calls the Resource Server.

The principal verification sequence at the Bank Issuer is:

1. Parse the VP assertion and identify the TPP.
2. Require an active registered TPP.
3. Enforce JTI replay, audience, association status, certificate status, freshness, and version checks.
4. Validate and consume the DAS challenge.
5. Verify the root Authorization Credential.
6. Verify the Delegation Credential and its relationship to the root credential and TPP.
7. Verify KB-JWT challenge bindings when present.
8. Require the TPP composite public key and verify the VP composite signature.
9. Decapsulate and authenticate the DAS-only encrypted package.
10. Compute the non-expanding scope intersection and issue a short-lived certificate-bound token.

Failures return an error; the hybrid cryptographic verification paths do not intentionally downgrade to classical verification.

## Cryptographic profile

| Role | Current implementation |
|---|---|
| Keycloak realm, ID token, and access token profile | ES384 integration backed by custom hybrid provider behavior |
| PKCE | S384 |
| Bank, Wallet, and TPP application signatures | Bouncy Castle composite `MLDSA65-ECDSA-P384-SHA512` |
| JOSE custom identifier | `MLDSA65-ECDSA-P384-SHA512` with `pqc_alg=p384_mldsa65` and composite public-key material |
| DAS confidential package | ML-KEM-768 decapsulation/encapsulation plus AES-256-GCM |
| Sender constraint | `cnf.x5t#S384`; no S256 fallback in the hybrid RS acceptance path |
| Protected TLS group list | `X25519MLKEM768:secp256r1:x25519`, with `X25519MLKEM768` ordered first |
| TLS protocol on protected proxy legs | TLS 1.3 |
| Crypto provider | Bouncy Castle 1.85 in the application modules |

The configured TLS group list contains classical groups after the hybrid group. Evidence must record the actually negotiated group rather than inferring it from configuration order.

## Keycloak extensions

The Bank image mounts custom providers and a patched Keycloak services JAR:

- `pqc-bank/mldsa-provider/`: hybrid key/signature providers, JWKS augmentation, client verification, PKCE policy code, and configuration resources.
- `pqc-bank/auth_server/pqc-x509-provider/`: client-certificate lookup integration for proxy headers.
- `pqc-bank/auth_server/pqc-signer/`: standalone signing/verification support used during provider development.
- `pqc-bank/auth_server/providers/`: built provider artifacts mounted into Keycloak.
- `pqc-bank/auth_server/patches/`: patched Keycloak service artifact mounted by Compose.

The Keycloak and Bank Issuer key discovery surfaces include `/hybrid-certs` and custom composite-key fields in addition to standard JWK fields.

## Component API map

The Wallet and TPP endpoint families parallel B1-C0. Important differences are cryptographic payloads and strict composite verification, not renamed business operations.

### Bank Issuer/DAS

- Discovery and keys: `GET /.well-known/openid-credential-issuer`, `GET /hybrid-certs`, `GET /jwks`, `GET /.well-known/jwks.json`
- Policy: `GET /api/policy/tpp-scopes/{tppClientId}`, `/api/policy/master-catalog`, `/api/policy/identity-claims`
- Issuance: `GET /offer/{type}`, `POST /credential`, `POST /api/internal/bootstrap-credential`
- Delegated authorization: `POST /api/v1/challenge`, `POST /token`
- Verification/status: `POST /introspect`, `POST /api/v1/verify-token`
- Health: `GET /health`

### Wallet

- Configuration/key APIs: `/api/config`, `/api/wallet-key`, `/api/jwks`
- OID4VCI APIs: `/api/fetch-offer`, `/api/receive-offer`, `/api/start-auth`, `/callback`
- Credential APIs: `/api/vcs`, `/api/delete-vc`, `/api/provision-scope-vc`
- Delegation APIs: `/api/delegate-request`, `/api/fetch-tpp-request`, `/api/delegate-requests`, `/api/delegate-status/{requestId}`, `/api/approve-delegate`, `/api/delegate-vcs/{requestId}`, `/api/send-to-tpp`
- Diagnostics: `GET|DELETE /api/protocol-log`

### TPP

- Configuration/policy: `/api/config`, `/api/tpp-allowed-scopes`, `/api/tpp-allowed-identity-claims`
- Delegation and presentation: `/api/request-delegate`, `/api/wallet-approve`, `/api/public/delegate-request/{requestId}`, `/api/public/submit-presentation`, `/api/poll-delegate`, `/api/receive-vcs`
- Token/resource: `/api/token`, `/api/request-token`, `/api/call-banking`, `/api/call-banking-api`
- State and diagnostics: `/api/state`, `/api/status`, `/api/reset`, `/api/protocol-log`

### Resource Server

The Open Banking and legacy banking resources parallel B1-C0. The acceptance path is different:

1. Require a compact JWT and known `kid` from Keycloak or Bank Issuer hybrid key material.
2. Call Bank Issuer `POST /api/v1/verify-token` for native composite verification.
3. Reject verification-service failure; there is no classical signature fallback.
4. Enforce expiration, audience, `cnf.x5t#S384`, and scopes.

Although the source labels this path local verification, the Node.js Resource Server currently makes a runtime HTTP call to Bank Issuer for composite verification. Benchmark and architecture documentation must count this dependency and its latency.

## State ownership

| Component | In-memory state |
|---|---|
| Wallet | Credentials, OAuth sessions, pending delegation requests, protocol log |
| TPP | Current TPP state, pending requests, protocol log |
| Bank Issuer | Issued VCs, issued access tokens, consumed JTI expirations, pending challenges |
| Resource Server | Cached Keycloak/Bank hybrid key material; SQLite business data |
| Keycloak provider | Generated hybrid key state owned by the provider runtime |

These stores are process-local. Restart and concurrent-session behavior must be tested explicitly.

## Known implementation constraints

- Runtime authorization state is memory-resident.
- Direct Debits endpoints are not implemented.
- Hybrid Resource Server verification adds a live dependency on the Bank Issuer verification endpoint.
- OQS proxy configuration advertises hybrid and classical groups; negotiated-parameter evidence is required.
- Provider artifacts and the patched Keycloak JAR must match their source/configuration digest for a valid build claim.
- Direct backend ports remain exposed for development and must not be confused with protected gateway paths during evaluation.
